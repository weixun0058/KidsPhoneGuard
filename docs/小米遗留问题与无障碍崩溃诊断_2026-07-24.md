## 2. 本次日志检查结论

### 2.1 无障碍掉线：已确认是应用主进程崩溃

本次不是用户关闭了无障碍权限，也没有证据表明是小米后台策略直接杀死应用。

02:06:31，`GuardForegroundService` 触发了 Android 的前台服务启动超时异常：

```text
AndroidRuntime: FATAL EXCEPTION: main
Process: com.kidsphoneguard, PID: 10830
android.app.RemoteServiceException$ForegroundServiceDidNotStartInTimeException:
Context.startForegroundService() did not then call Service.startForeground()

Caused by: Last startServiceCommon() call...
at GuardForegroundService$Companion.start(GuardForegroundService.kt:75)
at MainActivity.onResume(MainActivity.kt:94)
```

随后系统记录原进程死亡，并在约 5 秒后重新启动应用进程：

```text
02:06:31.980 am_proc_died  [10830,com.kidsphoneguard]
02:06:36.847 am_proc_start [13460,...,com.kidsphoneguard,...GuardForegroundService]
```

`GuardForegroundService` 和 `GuardAccessibilityService` 没有配置独立进程，因此前台服务异常会杀死整个应用进程，无障碍服务也会随之死亡。

### 2.2 当前处于“配置已开启，但服务已崩溃且未绑定”的假开启状态

崩溃后的系统状态同时满足：

- `accessibility_enabled = 1`
- 已启用组件列表仍包含 `com.kidsphoneguard/.service.GuardAccessibilityService`
- `dumpsys accessibility` 的 Bound services 中没有 KidsPhoneGuard
- Crashed services 中包含 `GuardAccessibilityService`

也就是说，系统设置页面和普通配置检查可能仍显示“已开启”，但真正执行拦截的无障碍服务已经不在运行。这正是“权限显示与实际状态不一致”的一个确定复现场景。

应用重启后日志也显示：

```text
aOperational=false
ar=false
heartbeat stale
```

虽然应用进行了恢复尝试，但本次没有让系统自动重新绑定无障碍服务。

### 2.3 直接原因与代码链路

当前链路为：

```text
MainActivity.onResume
  -> GuardForegroundService.start()
  -> context.startForegroundService()
  -> GuardForegroundService.onStartCommand()
  -> 本次启动请求没有及时重新调用 startForeground()
  -> HyperOS/Android 等待超时
  -> ForegroundServiceDidNotStartInTimeException
  -> 应用主进程崩溃
  -> 同进程的无障碍服务一起死亡
  -> 系统配置仍为 enabled，但服务不再 bound
```

相关结构：

- `MainActivity.onResume()` 每次恢复页面都会调用 `GuardForegroundService.start()`。
- `SetupWizardActivity.onResume()` 也会调用同一入口。
- `GuardForegroundService.start()` 使用 `startForegroundService()`。
- `startForeground()` 当前主要在 `onCreate()` 中调用。
- `onStartCommand()` 没有在入口处立即重新确认前台状态。

这与异常所指向的调用位置完全一致。小米系统当时为何把这个已经存在的服务重新视为“等待前台提升”仍属于系统内部状态，但应用没有对重复的 `startForegroundService()` 请求在 `onStartCommand()` 中立即确认前台状态，是可以确定的结构性缺口。

### 2.4 不是小米后台限制直接杀进程

崩溃前的应用日志显示：

```text
settings enabled=true
backgroundRestricted=false
ignoreBattery=true
```

系统同时给出了明确 Java 异常和主进程 FATAL 记录。因此本次不应归因于省电策略、后台限制或用户手动关闭权限。

## 3. “自我拦截”检查结果

### 3.1 日志没有发现普通应用拦截链拦截自身

用户点击/进入 KidsPhoneGuard 时，无障碍日志多次明确记录：

```text
应用 com.kidsphoneguard 在白名单中，跳过锁定
```

同一时间段没有发现以下证据：

- 没有针对 `com.kidsphoneguard` 的阻止决策；
- 没有 `OverlayService` 显示全屏遮蔽层的记录；
- 没有 `DegradedLockManager` 显示降级锁屏的记录；
- 没有把 KidsPhoneGuard 判定为卸载目标的 `uninstall_surface_block`；
- 没有由本项目 `NavigationExecutor` 发出的返回操作。

当时看到的返回键事件来自小米手势系统：

```text
GestureStubView_Left
onSwipeStop isFinish=true
injectBackKeyEvent
```

因此，现有日志不支持“规则引擎或遮蔽层直接拦截了自身”这一判断。

### 3.2 当前更可能的表象来源

较可能的情况有两类：

1. 应用界面被切走或表现异常，随后在 02:06:31 发生主进程崩溃，被用户感知为“自我拦截”；
2. 无障碍死亡后，保活服务检测到保护能力异常，相关恢复或降级状态造成了类似拦截的视觉效果。

但日志中缺少与用户看到的具体画面一一对应的记录，因此本项暂记为“未确认的自我拦截表象”，不能直接标记为已解决。下次复现时需要同时保留屏幕画面、精确时间点和 logcat。

补充说明：日志中的 Android `AppsFilter ... BLOCKED` 是系统的软件包可见性过滤，不是 KidsPhoneGuard 的应用拦截。

## 4. 小米问题汇总

### 4.1 已经用户真机确认

#### 重复出现三次遮蔽层

- 原现象：应该拦截的应用被拦截后，遮蔽层连续出现三次。
- 当前状态：用户已明确反馈“重复遮蔽层问题已解决”。
- 状态：已验收。

### 4.2 已改善但仍未解决

#### 防卸载仍有时间窗口

- 第一次长按桌面图标时，曾能立即拦截并收回卸载图标。
- 后续长按通常不能及时收回卸载图标。
- 点击卸载后，可以拦截卸载确认对话框，但检测和执行之间仍存在时间窗口。
- 用户反馈卸载成功概率已明显降低，但仍有一定概率能够完成卸载。
- 状态：进行中，不能关闭。

当前方案本质上仍是：

```text
系统先展示卸载入口或确认框
  -> 无障碍事件到达
  -> 扫描窗口和节点
  -> 判断是否正在卸载本项目
  -> 执行 BACK/HOME
```

只要系统界面显示、无障碍事件分发、节点扫描和导航动作之间存在延迟，就仍可能被快速点击穿透。

#### 防卸载扫描仍占用无障碍主线程

最近日志继续出现：

```text
uninstall_sweep_slow_scan ... 151-238ms
```

本轮 02:01 至 02:05 也多次出现约 170-212ms 的扫描。无障碍回调运行在应用主线程，这类耗时会直接扩大卸载时间窗口，也可能影响其他拦截响应。

状态：未解决。

#### 家长授权放行与超时恢复

状态：待专项测试。

## 6. 当前优先级建议

### P0：前台服务启动超时导致整个保护进程崩溃

这是本次无障碍掉线的直接原因。本轮已经完成以下代码修复：

1. `onCreate()` 在其他初始化工作之前立即提升为前台服务；
2. `onStartCommand()` 收到每次启动请求后立即重新确认前台状态；
3. 增加 `foreground_promotion_confirmed` 和异常堆栈日志。

界面已有的 operational 状态判断会同时检查系统配置、服务运行标志和心跳；仍需要本次新 APK 的真机验证。`MainActivity` 与 `SetupWizardActivity` 的重复启动入口暂时保留，用于服务恢复；当前修复使每次请求都满足 Android 的前台确认要求。

### P0：防卸载仍可被时间窗口穿透

应继续压缩长按菜单、卸载图标和确认框三个阶段的检测与导航延迟，并分别保留耗时日志。不能只依赖确认框阶段兜底。

### P1：削减小米无障碍主线程扫描耗时

资源 ID 定向和有限节点扫描虽然已经加入，但最近仍有 151-238ms 的慢扫描。需要按扫描入口和界面类型拆分耗时，找出仍然遍历过多节点的具体分支。

### P1：定位 3 秒 ShortcutService 调用源

给 UsageStats 相关子调用增加独立起止日志，确认是哪一个 API 导致小米桌面每 3 秒响应一次，再决定缓存、降频或改为事件驱动。

### P1：统一权限“配置状态”和“运行状态”

界面至少应分别呈现：

- 系统配置是否启用；
- 无障碍服务是否真实连接；
- 心跳是否新鲜；
- 前台保活服务是否正常；
- 小米专有权限是否仅为用户确认、还是能够读取真实状态。

### P1：补齐场景回归

依次验证历史任务恢复、自我拦截表象、设置内卸载、家长授权/超时恢复，最后进行荣耀真机回归。

## 7. 本次建议的恢复操作

当前设备仍可能处于“无障碍配置已开启、服务未绑定”的状态。继续真机测试前，需要在系统无障碍设置中：

1. 将 KidsPhoneGuard 无障碍服务关闭；
2. 再重新开启；
3. 返回应用后确认实际服务状态恢复，而不只看开关文字。

这只能恢复当前测试环境，不能替代代码修复。

6. 再分别验证普通应用拦截、自身应用进入和卸载防护。

## 9. 2026-07-25 真机结果纠偏

本节用于纠正此前仅依据静态代码作出的两项不准确描述。真机结果优先于代码推断。

### 9.1 “10分钟设置许可”只是最大截止时间，不是10分钟连续通行

配置向导点击任意非密码权限项时，代码会写入“当前时间 + 10分钟”的设置访问截止时间。但这个标志还有主动清除路径：

- 主页面 `MainDashboardScreen` 创建后立即调用 `clearSetupSettingsAccess()`；
- 家长配置页 `ConfigScreen` 创建后也立即调用 `clearSetupSettingsAccess()`。

因此实际语义是：

1. 从配置向导按钮直接打开对应系统权限页时，设置许可开始生效；
2. 只要返回主页面或家长配置页，许可就会立即清除，不等待10分钟；
3. 随后再从手机主页进入“设置 -> 权限页”，会立即恢复拦截；
4. 10分钟仅是没有触发主动清除时的兜底上限。

2026-07-25 小米日志与用户操作一致：

```text
02:18:13 setupAccess=true
02:18:15 返回家长配置页
02:18:18 setupAccess=false
```

日志也记录了通过配置向导直接进入权限页时：

```text
protected_settings_decision type=ALLOW
reason=setup_settings_access_allowed
```

用户真机确认：多数权限页可以从配置向导直接进入并调整；从主页的系统设置重新进入则会立即被拦截。

悬浮窗与无障碍页面停留约几十秒后被拦截的现象尚未由现有日志闭环。当前日志样本在 `setupAccess=true` 时持续返回 ALLOW，没有捕获对应的 BLOCK 记录。下一次复现需要记录许可的设置来源、主动清除来源、截止时间以及实际 BLOCK 决策，不能再直接归因于“10分钟到期”。

### 9.2 `gradlew installDebug` 不是普通安装器升级，两台 ROM 的实际链路不同

用户真机结果：

- 荣耀：全局解锁关闭时，`.\gradlew.bat installDebug` 无法完成升级；
- 小米：全局解锁关闭时，同一命令可以完成升级。

当前小米设备的包管理状态为：

```text
installerPackageName=null
initiatingPackageName=com.android.shell
```

这说明小米的 `installDebug` 由已授权 ADB shell 直接替换应用，没有进入可见的 MIUI 安装器页面。无障碍守卫没有窗口或点击事件可以拦截，因此全局解锁状态无法阻止这条特权安装通道。

荣耀的实际结果说明其固件/设备配置在 ADB 安装过程中存在可见安装确认或其他会被现有守卫中止的步骤。当前没有同一时段的荣耀日志，具体组件仍以用户真机结果记录，不凭代码猜测包名。

因此应区分：

| 升级通道 | 全局解锁关闭时的预期/现状 |
| --- | --- |
| 用户点击 APK、应用市场或可见系统安装器 | 由普通安装器/市场保护拦截；小米与荣耀原则一致 |
| 小米已授权 ADB shell 直接安装 | 当前可以绕过应用层无障碍保护 |
| 荣耀 `installDebug` | 用户真机确认当前会被阻止 |

仅靠普通应用的无障碍服务无法可靠否决系统授权的 ADB shell 包替换。若产品要求连已授权 ADB 安装也必须受控，需要 Device Owner/企业设备策略、关闭 USB 调试或系统级安装限制；这超出当前普通本地应用权限能力，不能用增加安装器关键词伪装修复。
