## 零、清理思路与方法

### 0.1 清理原则

本项目经历多轮迭代（初始开发 → 商业化评估 → 无障碍掉权诊断 → flavor split → 服务解耦重构），过程产生了大量中间产物。清理遵循以下原则：

1. **构建优先**：删除任何文件前，确保 `./gradlew.bat :app:assembleDebug` 能通过。
2. **源码即真相**：`settings.gradle.kts` 声明了哪些模块参与编译，未声明的视为死代码。
3. **近期决策优先**：2026-05-24 的解耦计划文档是当前架构的源文件，保留；2026-02 的初期开发文档已被后续决策覆盖，可以归档。
4. **区分跟踪状态**：文件是否被 `git ls-files` 识别决定了操作方式是 `git rm` 还是直接 `Remove-Item`。
5. **日志与 dump 不是资产**：`forensics/`、`*.log`、`adb_*_trace.txt` 是运行时取证快照，不构成可维护的项目知识。
6. **重复副本不留**：`CLAUDE.md` 与 `AGENTS.md` 内容几乎一致，保留后者。

### 0.2 分类决策树

```
文件是否在 settings.gradle.kts 声明的模块中？
  ├── 是 → 是否参与编译？
  │   ├── 是 → A 类（关键代码）
  │   └── 否 → C 类死代码（如 observer/）
  └── 否 → 是否为项目知识资产？
      ├── 是 → 是否仍有参考价值？
      │   ├── 是 → B 类（必要支撑）
      │   └── 否 → C 类（过时文档/历史报告）
      └── 否 → 是构建产物、日志、截图、缓存？
          └── 是 → C 类（垃圾文件）
```

### 0.3 扫描方法

1. `Get-ChildItem -Recurse` 遍历全项目目录，排除 `.git/`、`.gradle/`、`build/`、`.idea/`
2. `git ls-files` 逐目录确认 Git 跟踪状态
3. 读取 `settings.gradle.kts`、`build.gradle.kts`、`app/build.gradle.kts` 确定活动模块
4. 读取 `.gitignore` 与 Git 跟踪状态对比，发现"先跟踪后忽略"的历史遗留
5. 对存疑文件（如 `issues_list.md`）读取内容确认其性质

### 回滚方案

如果阶段 2 或 4 之后发现问题，可以回滚：

```powershell
# 如果尚未提交（阶段 2 之后）：
git reset --hard HEAD

# 如果已提交（阶段 4 之后）：
git revert HEAD
```

> **注意**：阶段 1 删除的未跟踪文件无法通过 Git 回滚。如需保留，请在执行前手动备份 `forensics/` 等目录。

### 可选：缩小仓库体积

`git rm` 会移除文件但保留 Git 历史（`.git` 目录不会立刻缩小）。如需物理缩减 `.git` 目录体积：

```powershell
git gc --aggressive --prune=now
```

此操作风险低但效果有限（日志文件约 18 MB 的 blob 仍保留在历史中）。要彻底清除大文件历史需使用 `git filter-repo` 或 `git filter-branch`，风险较高，不建议在本次执行。

## 七、风险评估与遗留问题

| 风险项 | 等级 | 说明 |
|---|---|---|
| 清洗后构建失败 | **必须验证** | 清洗后立即执行 `./gradlew.bat :app:assembleDebug` |
| `mipmap` 图标兼容性 | 中 | 仅含 `mipmap-anydpi-v26`，低版本设备可能无图标，建议后续补充传统 dpi 图标 |
| `issues_list.md` 处置 | 低 | 如需保留历史问题记录，阶段 2 中将 `git rm` 替换为 `git mv issues_list.md docs/` |
| `observer/` 历史价值 | 低 | `git rm -r` 后文件仍可在历史 commit 中查看。如需彻底抹除历史需 `git filter-repo`，不建议在本次执行 |
| 清洗后 `.git` 体积 | 低 | `git rm` 不移除历史 blob，仓库物理体积不会立刻缩小。大文件（16 MB trace）仍保留在历史中 |
