> 评价日期：2026-07-09
> 评价范围：`app/src/main` 全量源码（约 12,779 行 Kotlin）、`docs/plans` 重构计划与收尾报告、构建配置与脚本
> 评价方法：源码通读 + 指标采集（行数 / TODO / 测试覆盖）+ 架构链路追踪
> 配套解读：第八节《重点问题通俗解读》用大白话解释了本节列出的若干"看不懂"的问题，建议结合阅读。

## 一、总体评价（结论先行）

项目是一个**完成度较高的本地防沉迷 MVP**，核心管控闭环（配置 → 决策 → 拦截 → 统计 → 自我保护）已经跑通，并经过一轮有计划、有收尾的模块化重构（Phase 1–7）。代码工程素养明显高于一般个人项目：统一的 KDoc「输入/输出」注释规范、统一的 `GuardActionResult` 路由结果、可测的纯函数提取、signature 广播与 PBKDF2 密码等安全基线已就位。

主要短板集中在三处：**①绕过类风险**（依赖系统时间校验、设置守卫的关键词/OEM ROM 覆盖需持续补足）、**②状态一致性债务**（全局锁双源、遮罩静态状态竞态）、**③工程化缺口**（破坏性数据库迁移、UI 巨型文件、测试覆盖断层、无依赖注入）。这些问题不影响 MVP 演示，但会在真实长期使用和多设备适配中暴露。

> 📝 **关于"白名单前缀匹配绕过"的更正**：本报告早期版本曾把"白名单前缀匹配"列为 P0 绕过风险。经代码复核，这是一处误诊——前缀匹配实际用于「拦截设置类表面」而非「放行白名单」，方向恰好相反；面向普通儿童的产品里"包名伪装"威胁也不成立。该条已撤销，详见第六节与第八节第 4 点的完整说明。

**一句话定性**：架构方向正确、重构纪律良好，但安全抗绕过与数据持久化稳健性需在「可用」迈向「可信」之前补齐。

## 二、架构设计评价

### 合理之处

1. **单向数据流，引擎只读**
   `ConfigActivity/SetupWizard → Repository → Room/SharedPreferences → LockDecisionEngine（只读）→ AppBlockCoordinator → OverlayService/NavigationExecutor`。决策引擎不写存储，规则变更自动生效，无需重启服务。这是本项目最核心、也最正确的架构决策。

2. **组合根模式（Phase 7 成果）**
   `GuardAccessibilityService` 从「上帝服务」被精简为**生命周期入口 + 组合根**，业务逻辑下沉到 `accessibility/`、`block/`、`guard/` 三族协作者。职责边界清晰，单文件可控（467 行），其中纯函数和显式依赖协作者可独立单测；仍依赖 Android Framework/私有装配的协作者需要进一步可测化。

3. **显式事件路由 + 顺序短路**
   `AccessibilityEventRouter` 用 `runRouteSteps(vararg steps)` 显式编码路由顺序并短路，路由顺序（省电模式 → 系统面板 → 受保护设置 → 自身应用 → 视频号 → 引擎初始化 → block hold → 去抖 → 白名单 → 常规策略）可见、可读、可测。`runRouteSteps` 为 `internal` 纯函数，便于单测。

4. **统一结果类型 `GuardActionResult`**
   `Continue / Consumed / ScheduleFollowUp` 统一路由结果，避免布尔返回值丢失语义，降低协调器间耦合。

5. **可提取的纯逻辑引擎层**
   `LockDecisionEngine` 的时段判断等逻辑可提取为纯函数并单测；但引擎实例本身仍依赖 `Context`、`KidsPhoneGuardApp` 与 repository/settings，不能称为完全脱离 Android Framework。

### 架构风险

1. **手动依赖装配，无 DI 框架**
   `GuardAccessibilityService` 用大量 `by lazy` + 构造函数注入装配协作者，`AppBlockCoordinator` 构造参数约 **30 个**、`ProtectedSurfaceGuard` 同样依赖大量回调 lambda。优点是零框架、启动快；缺点是**装配代码脆弱、新增依赖时改动面大、易错传回调**。随功能增长会越来越难维护。

2. **`OverlayService` 静态状态跨入口**
   遮罩显隐状态以 `companion object` 静态字段 + `stateLock` 管理，被 `AppBlockCoordinator`、`ProtectedSurfaceGuard`、`UsageTrackingManager` 等多入口读写。虽有 `synchronized` 与 `OverlayCoordinator` 收口，但「谁有权改状态」未集中，仍存在闪烁/漏隐藏的竞态窗口。

3. **功能删除留痕**
   Phase 8（敏感动作/防卸载）已标记 **Obsolete** 并从运行时移除，但 `AppBlockerService` 作为废弃空壳仍留在 manifest 与代码中，`AndroidManifest` 仍注册其 `foregroundServiceType`。废弃代码未彻底清理会造成认知负担。

## 三、代码质量评价

### 优点

- **注释规范统一**：几乎所有公共方法都有 KDoc，且采用「输入：… / 输出：…」固定句式，可读性高。
- **异常处理到位**：服务/协程入口普遍 `try/catch` 并 `Log.e(TAG, ..., e)`，不让异常从服务逃逸。
- **日志纪律**：`private const val TAG = "ClassName"` 一致；`GuardForegroundService` 有完善的取证日志（health_snapshot / accessibility_forensics / drop_detected）。
- **零 TODO/FIXME 噪音**：全仓 `TODO/FIXME/XXX/HACK` 计数为 0，债务集中在 `docs/plans` 跟踪而非散落代码。
- **可测性设计**：纯函数提取到 `companion object` 的 `internal` 方法（如 `shouldSkipDuplicateOverlay`、`runRouteSteps`），单测可直达。

### 问题

1. **UI 巨型文件**
   评审基线为 `ConfigActivity.kt` **2428 行**、`MainActivity.kt` **1313 行**，单文件堆叠 20+ Composable（批量配置、应用选择、时段选择、规则卡片等）。维护、合并冲突、定位问题都困难，应按功能拆分到独立文件。2026-07-12 已启动两阶段：规则、当天用量和临时奖励状态及对应写入迁至 `ConfigViewModel`/`StateFlow`，应用选择组件迁至 `ui/config/AppSelectorComponents.kt`，`ConfigActivity` 降至 2110 行；批量/单规则编辑组件与 `MainActivity` 重构仍未完成，不能据此把该问题标为已修复。

2. **反射 + Shell 兜底（死代码路径）**
   `AppBlockCoordinator.tryForceStopApp` 使用反射调用隐藏 API `ActivityManager.forceStopPackage`，并 `Runtime.getRuntime().exec("am force-stop ...")` 兜底。反射在受限 Android 版本/非系统应用下大概率失败，shell exec 在非 root 下亦无效，属于「写了但多数设备不生效」的死代码路径，且引入安全隐患。建议明确降级为「前台压制」策略并删除无效路径。（通俗解读与修法详见第八节第 1 点）

3. **魔法延时数组散落**
   `forceStopDelaysMs`、`fallbackNavigationDelaysMs`、`releaseCheckDelays`、`protectedSurfaceNavigationBurstDelays` 等大量硬编码延时数组，分散在 `GuardAccessibilityService`（装配处）与各协调器中，无统一配置点，调参困难。这些数组本质是一组「连击重试」的毫秒排程，通俗解读与集中化修法详见第八节第 2 点。

4. **`fallbackToDestructiveMigration`（严重）**
   `AppDatabase` 使用破坏性迁移。任何 schema 变更（加字段、改类型）都会**清空家长配置的全部应用规则与使用记录**。对已上线用户是灾难性体验，必须在正式发布前改为显式 Migration。（已发生实锤与修法详见第八节第 3 点）

5. **遗留明文密码分支（已修复）**
   `PasswordManager` 已于 2026-07-11 移除运行时明文验证：旧安装若仅有明文，会在应用初始化时先迁移为 PBKDF2 再删除明文；已有 hash 的残留明文则直接清除。这样既缩小本地读取攻击面，也不丢失既有家长密码。

## 四、技术选型评价

| 选型 | 评价 |
| --- | --- |
| Kotlin + Jetpack Compose + Material3 | ✅ 合理，现代 Android 标准栈，UI 声明式适合配置类界面 |
| Room + Coroutines Flow | ✅ 合理，响应式数据流与单向数据流契合 |
| MVVM + 单向数据流 | ✅ 合理，引擎只读、UI 写库的模型清晰 |
| 前台服务 `specialUse` | ✅ 合理，Android 14 合规的前台服务类型 |
| signature 级自定义广播权限 | ✅ 合理，防外部应用触发拦截广播 |
| PBKDF2-HMAC-SHA256（120k 迭代） | ✅ 合理，符合当前密码存储实践 |
| 手动依赖装配（无 Hilt/Dagger） | ⚠️ MVP 可接受，长期会成负担 |
| `UsageStatsManager` 3 秒轮询 | ⚠️ 简单可靠但耗电，可向事件驱动演进 |
| `fallbackToDestructiveMigration` | ❌ 不适合带用户数据的生产应用 |

总体选型务实、无过度设计，与「纯本地 MVP」定位匹配。唯一明显不当是破坏性迁移策略。

## 六、待解决问题清单（按优先级）

> 本清单是「索引」。每条若看不懂，请跳到第八节对应编号看通俗解读。

### P0 — 安全抗绕过（发布前必修）

1. **系统时间篡改绕过**
   时段禁用（`LocalTime.now()`）与每日限额重置（`LocalDate.now()`）均依赖设备系统时间。儿童改系统时间/日期即可绕过。应引入网络时间校验或对时间倒拨做异常取证。

   > 📝 **更正说明**：早期版本此处另列有一条"白名单前缀匹配绕过"，建议"收紧为精确匹配"。经代码复核为误诊，已撤销——前缀匹配是「拦截设置」的触发器（`isSettings` 命中即 `shouldBlock=true`），不是「放行白名单」；改成精确匹配反而会漏掉 OEM 管理器（小孩正好从那里关权限），是退化。完整论证见第八节第 4 点。

### P1 — 抗绕过的真实杠杆 + 数据/状态一致性

2. **设置守卫内容策略覆盖（攻防核心，持续投入）**
   防小孩"进设置关权限 / 开省电模式破防"的真正杠杆是 `ProtectedSettingsPolicy` 的逐页内容判定（`ALLOW/OBSERVE/BLOCK_ACTION/BLOCK_PAGE`），而非包名匹配。需持续补：`targetAppKeywords`（页面提到本应用名）、`riskyCapabilityKeywords`（权限页）、`riskyActionKeywords`（禁用/卸载/强停等点击）、`guardianDisruptive*`（省电模式），按 MIUI/EMUI/ColorOS/OneUI 等逐 ROM 覆盖；并调 `BLOCK_ACTION`（只拦危险点击、页面留着）与 `BLOCK_PAGE` 的粒度，做到"设置可进、危险动作拦死"。这与现有未决 ISSUE（"保护设置关键词与响应速度调优"）一致。详见第八节第 4 点。

3. **破坏性数据库迁移**
   `AppDatabase.fallbackToDestructiveMigration()` 会在 schema 变更时清空所有规则与使用记录。改为显式 `Migration`，并开启 `exportSchema` 留存迁移基线。
   > 📌 **已发生实锤**：git 历史显示 v1→v2 仅给 `app_rules` 加了一列 `limitMode`，但因全程无 `Migration`，凡从 v1 升级到 v2 的用户数据已被静默清空（发生在 `9e536a4` 提交）。这是已发生的真实丢失，不是"未来隐患"。详见第八节第 3 点。

4. **全局锁双源**
   `SettingsManager.isGlobalLockEnabled()` 与 `AppRule.isGlobalLocked` 两处来源，`LockDecisionEngine` 同时判断两者，可能出现不一致。统一为单一真相源。

5. **遮罩静态状态竞态**
   `OverlayService` 静态显隐状态多入口修改。集中到单一 `OverlayCoordinator` 读写入口，移除外部直接调用 `OverlayService.showOverlay/hideOverlay`。

### P2 — 工程化与健壮性

6. **UI 巨型文件拆分**
   `ConfigActivity.kt`（2428 行）、`MainActivity.kt`（1313 行）按功能域拆分为多文件。

7. **无效 force-stop 路径清理**
   `AppBlockCoordinator.tryForceStopApp` 中反射 `forceStopPackage` + `am force-stop` shell 多数设备无效，删除或明确降级为前台压制，避免死代码与误判。（通俗解读详见第八节第 1 点）

8. **输入法豁免改运行时发现（完整性修复，非安全修复）**
   `isInWhitelist` 里两个输入法前缀（`com.android.inputmethod`、`com.google.android.inputmethod`）只覆盖 AOSP/Gboard 等少数键盘，漏掉三星 `honeyboard`、OPPO/vivo/魅族/荣耀自带键盘——这些手机上键盘一弹就被拦，导致全机打不出字、连家长密码都输不了。改用 `InputMethodManager.inputMethodList` 运行时取已装输入法精确包名。**注意定性**：这是为"别漏掉品牌键盘"的完整性修复，**不是防 spoofing**（普通儿童造不出冒牌包名，该威胁对本产品不成立）。详见第八节第 4 点。

9. **取证日志增长**
   `accessibility_forensics.log` 有 2MB 轮转，但 PC 侧 `timeline.jsonl` 持续追加无上限，长期会膨胀。加滚动/容量上限。

10. **密码明文分支淘汰计划**
    设定版本节点强制迁移并移除 `KEY_LEGACY_PASSWORD` 明文读取。

11. **`WRITE_SECURE_SETTINGS` 预留项收口（勘误：无需修复）**
    原报告误称无实现。复核确认 `DegradedLockManager.tryProgrammaticRecovery()` 已在 ADB 授权场景通过 `Settings.Secure` 程序化恢复无障碍；应保留声明，并在 README/AGENTS 中表述为已实现的高级/企业能力。

### P3 — 可维护性与扩展性

12. **测试覆盖断层**
    审计时共有 14 个测试文件覆盖协调器/守卫/路由。后续已补时段判定、可信时间和旧密码迁移的纯逻辑单测，但 **完整 `LockDecisionEngine`、`PasswordManager` 的 SharedPreferences 路径、`DailyUsageRepository`、`GuardForegroundService`、全部 UI** 仍缺充分测试；引擎与密码应继续优先补测。

13. **无依赖注入框架**
    手动装配在协作者 ~30 个参数规模下已显脆弱。引入 Hilt/Koin 或至少构造配置数据类收敛参数。

14. **债务跟踪碎片化**
    `issues_list.md` 在清理中被删除，issue 状态散落在各 phase closeout。建议重建单一 issue 跟踪文件（如 `docs/ISSUES.md`）。

15. **轮询优化**
    `UsageStatsManager` 3 秒持续轮询，可在夜间/熄屏降低频率或向事件驱动演进以省电。

16. **系统受保护表面分类器拆分（已修复）**
    `isLauncher`/`isPhoneApp`/`isMessagingApp`/`isCommunicationApp` 已删除；设置、安装器和应用市场识别已迁移至 `SystemSurfaceClassifier`，与 `WhitelistManager` 的放行职责彻底分离。设置前缀匹配逻辑保持不变，降低了把“拦设置”误读成“白名单绕过”的认知风险。详见第八节第 4 点。

## 七、维护与扩展性建议

1. **先补「可信」再扩「功能」**：P0/P1 修复前不建议开始网络模块——抗绕过与数据持久化是远程管控的地基，地基不稳则远程下发规则可被本地绕过。
2. **重建 issue 台账**：将散落在 phase 文档中的 ISSUE-004/005、双源锁、白名单等汇总进 `docs/ISSUES.md`，按本报告优先级排序跟踪。
3. **拆 UI 同时抽 ViewModel**：拆分 ConfigActivity 时顺手补 ViewModel + StateFlow，为后续网络模块的远程状态注入留接口。
4. **明确防卸载的产品决策**：Phase 8 废弃后无防卸载，需确认是否接受「儿童可卸载 App」这一现状；若不接受，应规划替代方案（如设备管理员/Owner 模式），而非恢复已废弃的敏感动作拦截。
5. **真机回归优先于新功能**：Phase 7 的设备回归清单是当前最高性价比的收尾动作，建议在引入任何新功能前完成。
6. **修改纪律（强烈建议）**：后续任何代码修改都应先在本报告或 `docs/ISSUES.md` 列「详细修改清单与步骤」，逐条改、逐条验证、逐条更新状态，避免文档与代码再次脱节。改动涉及上述 P0/P1 问题时，务必同步更新本报告对应条目。

## 八、重点问题通俗解读（防"不知所谓"）

本节用大白话解释第六、第三节里几个最容易看懵的问题。每条都附「说的是哪部分功能 / 为什么是问题 / 根因 / 建议修法」。

### 第 1 点：反射 + Shell 兜底（force-stop 死代码）

**说的是哪部分功能？**
拦截执行链里"尝试强停目标 App"这一步（`AppBlockCoordinator.tryForceStopApp`）。

**代码实际做了三件事：**
1. 公开 API 清理（有效）：`finishAndRemoveTask()` 清任务栈、`Process.killProcess()` 杀进程、`killBackgroundProcesses()` 杀后台。这三步是官方公开、普通 App 能用的。
2. 反射调用隐藏 API `ActivityManager.forceStopPackage`（行 514–525）。
3. `Runtime.getRuntime().exec("am force-stop ...")` shell 兜底（行 527–531）。

**为什么写了等于没写？**
`forceStopPackage` 背后要校验权限 `android.permission.FORCE_STOP_PACKAGES`，其级别是 `signature | system | privileged`——只有系统签名应用或 system UID 才能持有。本项目是家长自己装的普通第三方 App，根本拿不到。于是：
- 反射路径：要么因无权限抛 `SecurityException`（代码自己 catch 了），要么在 Android 9+ 的"非 SDK 接口限制"下反射直接失败，`invoke` 到不了实际逻辑。
- shell 路径：以本 App 自己的 UID 执行，同样无 system 权限，结果还是 `Permission Denial`（除非设备已 root）。

**结论**：对"非系统、非 root"的部署形态，第 2、3 段在任何消费级设备都不会产生效果。真正起作用永远只有第 1 段。

**隐患不止"死代码"：**
- 反射出现在拦截热路径，定制 ROM 行为不一致，少数情况可能触发崩溃/ANR，反而让监控链路变脆弱；
- `exec("am force-stop $packageName")` 把变量拼进 shell 字符串，规范写法应传参数数组 `exec(arrayOf("am","force-stop",packageName))`，避免 shell 解析；
- 最隐蔽的是**制造虚假安全感**：维护者看到这段会以为"强停是兜底的"，于是不补真正可靠的压制手段，安全网其实并不存在。

**建议修法：**
删除第 2、3 段，让拦截明确只依赖「HOME/BACK 返回桌面 + 红屏遮罩」的前台压制（本项目 `GuardAccessibilityService` + `OverlayService` 已经在做，且这才是家长管控 App 可靠、不依赖隐藏权限的正路）。真想要"杀进程/隐藏应用"效果，应走 Android 官方家长控制通道（`DevicePolicyManager` / 设备所有者模式），而不是在普通 App 里硬撬系统接口。

### 第 2 点：魔法延时数组散落

**说的是哪部分功能？**
拦截与守卫里那些"连击重试"的毫秒数组。基于无障碍的拦截无法保证一次动作就成功（目标 App 可能还在启动动画、系统响应慢、用户快速操作），所以代码采用"连击"策略：事件发生后，在一系列递增延时点上各试一次同一动作，增加命中概率。

**当前散落在哪些地方：**

| 数组 | 定义位置 | 值 | 作用 |
|------|---------|-----|------|
| `forceStopDelaysMs` | GuardAccessibilityService 注入 | `[120, 360, 700]` | 拦截后在 120/360/700ms 各试一次强停（即第 1 点说的死路径） |
| `fallbackNavigationDelaysMs` | 同上注入 | `[650, 1200]` | 拦截后补两次 HOME/BACK 兜底导航 |
| `protectedSurfaceNavigationBurstDelays` | 同上注入 | `[0, 60, 140, 280, 800, 1500, 3000]` | 受保护界面"导航压制爆发"：0 即立刻执行，随后密集再转稀疏，把钻向设置/安装器的动作在启动窗口内"打下来" |
| `releaseCheckDelays`（两份） | 各自写在协调器方法内 | AppBlockCoordinator `[1500,2800,4200]`；ProtectedSurfaceGuard `[900,1600,2600,4200]` | 遮罩释放检查排程 |

**为什么"散落"是问题：**
1. 分布在三个文件、来源不一致（有的走构造注入、有的写死在方法里）；
2. 同一概念复制漂移——`releaseCheckDelays` 被复制成两份、值不同、长度不同，将来想统一调节奏极容易只改一处；
3. 数字是"魔法数字"无语义：为什么是 `120/360/700`？设计意图全藏在数字里；
4. 调参要翻箱倒柜；加上同类散落的标量（`huaweiFallbackDelayMs`、`blockCooldown`、`overlayReshowCooldown`、`WECHAT_FINDER_COOLDOWN_MS` 等），整个延时体系无集中视图。

**建议修法（纯搬移、低风险）：**
新建单点配置（如 `service/block/GuardTiming.kt` 的 `object GuardTiming`），把所有延时数组与标量收进去，每个带意图注释，协调器改为引用。这样①一个文件管全部延时；②消除 `releaseCheckDelays` 复制漂移；③意图写进注释；④为 ISSUE-005 机型适配铺路（将来把 `object` 升级成 `data class` + `forOem()` 工厂即可给不同 ROM 一套延时）。注意 `GuardTiming` 仍用 `longArrayOf(...)` 暴露 `LongArray`，避免改动一堆构造签名。改完跑一次 `./gradlew lint`。

### 第 3 点：`fallbackToDestructiveMigration`（破坏性数据库迁移）

**说的是哪部分功能？**
和任何界面、按钮都无关——它说的是 App 背后"记设置"的那张本地数据库表的升级机制。本 App 的核心价值就是家长给孩子每个 App 设的规则（哪个禁玩、哪个限时、几点到几点不能开）以及每天使用了多久的统计，这些全存在手机本地这张表里。

**为什么会出问题？**
Room 在打开数据库前，会把声明的 `@Database(version = N)` 和手机里实际存在的库版本对比。正确做法是：每次改动表结构（加字段等），写一段 `Migration(old, new)` "搬运脚本"，把老用户的旧表数据原样搬进新表。但本代码调了 `.fallbackToDestructiveMigration()` 且全仓无任何 `Migration` 定义——这等于告诉 Room："要是你不会搬，就直接把整张旧表 DROP 掉、建张空表。" 翻译成人话：**家长一更新 App，之前设的所有规则和使用记录全没了，而且悄无声息——App 不报错、照常能打开。** 对别的 App 可能只是少点缓存，对这个 App 是"命根子被清空"，因为家长费劲配的规则就是它的全部价值。

**已发生的真实事故（不是假设）：**
git 历史锁定了 v1→v2 的真实差异：v1 的 `app_rules` 表没有 `limitMode` 列；v2（提交 `9e536a4`，"优化配置界面并完善批量规则反馈"）把 `version` 从 1 改成 2，并给 `AppRule` 新增一列 `limitMode`。也就是说这次结构改动其实**只加了一列**，但因为全程没有 `Migration`、破坏性迁移又开着，**每一个从 v1 升级到 v2 的用户，其全部应用规则和使用记录都已被静默清空**。未来任何人再 bump 版本（比如再加个字段），同样会再清一次。这就是报告把它标"严重"的原因。

**建议修法（对症、最小、低风险）：**
因为差异只有"加一列 `limitMode INTEGER`（`LimitMode` 枚举以 `Int` 存、`BOTH=0`、非 null → `DEFAULT 0`）"，修复很干净——在 `AppDatabase.kt` 补：

```kotlin
@Database(entities = [AppRule::class, DailyUsage::class], version = 2, exportSchema = true)
abstract class AppDatabase : RoomDatabase() {
    // ...
    private val MIGRATION_1_2 = object : Migration(1, 2) {
        override fun migrate(db: SupportSQLiteDatabase) {
            db.execSQL("ALTER TABLE app_rules ADD COLUMN limitMode INTEGER NOT NULL DEFAULT 0")
        }
    }
    // databaseBuilder(...).addMigrations(MIGRATION_1_2)   // 用显式迁移替代 destructive
    // 关键：彻底删除 .fallbackToDestructiveMigration()
}
```

往前看：① 每次改表都必须 bump version + 新增对应 Migration；② 开 `exportSchema = true` 并在 `app/build.gradle.kts` 配 `room { schemaDirectory ... }`，导出各版本 schema；③ 补一个 `MigrationTestHelper` 的 `androidTest`，写入 v1 假数据→触发迁移→断言 v2 数据还在（验证"迁移不丢数据"的金标准）；④ SQLite 只支持 `ADD COLUMN`，改名/删列要走"加新列→拷数据→删旧列"或 Room 2.4+ 的 `@AutoMigration`（依赖已导出 schema 历史）；⑤ 若真想对"太古老已不在乎"的版本允许清空，可用 `fallbackToDestructiveMigrationFrom(intArrayOf(1))` 限定只对 v1 兜底，而非对所有版本。被 `9e536a4` 清空的那些数据无法挽回——这是教训。

### 第 4 点：白名单 / 设置拦截（澄清一处误诊，并讲清来龙去脉）

> 这一节点名曾是"白名单前缀匹配绕过"。经代码复核，那是个误诊，方向恰好相反。本节把它彻底讲清楚，避免后续维护者再被误导。

#### 4.1 先讲产品要解决的真实问题

这个 App 面对的是**普通儿童**——他们没有写代码、造包名的能力，但会"用手机"。攻防测试中发现，孩子最有效的破防路径是：**进入系统"设置"（或各厂商的系统管理器），在里面关掉本应用的权限、或开启省电模式，让监控失效**。所以产品策略是：**把"设置"这类表面严控起来，让孩子进不去、或进去了也做不了危险动作。**

但"设置"又不能一刀切全锁——里面有很多必须能用的东西（联网、亮度、蓝牙……）。于是就产生了核心矛盾：**设置既要拦、又要放，且要精确到"哪个页面/哪个动作"的粒度。** 本节要讲清楚的就是：代码是怎么解这个矛盾的，以及"前缀匹配"在这个解法里到底扮演什么角色。

#### 4.2 代码里有两套**完全独立**的机制，别混为一谈

这是最容易晕的根源。两套机制名字里都带"白名单/包名"，但职责相反：

**机制 A：豁免白名单 `isInWhitelist` —— "这些 App 绝不碰"**
- 干什么：判定一个 App 是否**完全免于拦截**。命中=永远不拦、家长也无法给它加规则、配置列表里直接隐藏。
- 谁在里面：`SYSTEM_WHITELIST`，一个约 200+ 个**精确包名**的硬编码集合——桌面、拨号、通讯录、短信、相机、各 OEM 安全中心/应用市场等。这就是当初"强制加白名单"诉求的落点，是产品决策、精确匹配、应保留。
- 唯一的前缀通配：只有**两个输入法前缀**（`com.android.inputmethod`、`com.google.android.inputmethod`），目的是别把键盘拦了（见 4.4）。
- 消费点：`AppBlockCoordinator`（命中则跳过拦截）、`AppRuleRepository`（命中则不让加规则）、`ConfigActivity`（命中则从配置列表隐藏）、`AssistantOverlayRoutingSupport`（命中则不弹助手浮窗）。

**机制 B：设置拦截触发器 `SystemSurfaceClassifier.isSettingsSurface`（前缀匹配）—— "这是设置类表面，要拦/要盯"**
- 干什么：判定一个包名是否属于"设置/系统管理器"家族。命中=**触发拦截**，不是放行。
- 关键代码（`LockDecisionEngine` 第 53 行）：
  ```kotlin
  if (SystemSurfaceClassifier.isSettingsSurface(packageName)) {
      return BlockDecision(shouldBlock = true, reason = BlockReason.APP_BLOCKED, appName = "系统设置")
  }
  ```
  命中前缀 → 直接 `shouldBlock=true` → 把孩子挡在设置门外。这恰是 4.1 说的"严控设置"的实现。
- 命中后还会进入 `ProtectedSurfaceGuard` → `ProtectedSettingsPolicy` 做**逐页内容判定**（见 4.3），决定这个设置页面是放行、只观察、拦某个点击、还是整页拦。

**一句话区分**：机制 A 是"白名单=放行"，机制 B 是"前缀=拦截"。早期报告把它们混为一谈，把"拦截用的前缀"当成了"放行用的白名单漏洞"，于是得出"收紧前缀"的错误建议。

#### 4.3 真正的攻防杠杆：`ProtectedSettingsPolicy` 的逐页内容判定

这是解 4.1 矛盾的核心，也是后续该投入的地方。它不看包名，而是**读取当前设置页面的文本/控件/点击内容**，按关键词判定：

| 决策类型 | 含义 |
|---------|------|
| `ALLOW` | 放行（如 benign 设置页、或全局解锁时） |
| `OBSERVE` | 只记录、不拦（如候选设置页但无危险信号） |
| `BLOCK_ACTION` | **只拦那个危险点击，页面留着**（如点了"禁用权限""卸载""强停"） |
| `BLOCK_PAGE` | 整页拦（如目标应用权限页、华为省电模式页） |

关键词分几类（来自 `BrandSettingsRules`，按品牌 ROM 配置）：
- `targetAppKeywords`：页面提到本应用名 → 孩子想进本应用的"应用信息"页（那里能关权限/卸载）。
- `riskyCapabilityKeywords` / `riskyActionKeywords`：权限页 / 危险动作（禁用、卸载、强制停止）。
- `guardianDisruptiveCapabilityKeywords` / `guardianDisruptiveActionKeywords`：省电模式（孩子开省电来杀后台服务）。

**这套四态决策才是"设置可进、危险动作拦死"的正确架构**，对应未决 ISSUE"保护设置关键词与响应速度调优"。后续工作应集中在这里：按 MIUI/EMUI/ColorOS/OneUI 等逐 ROM 补关键词、调 `BLOCK_ACTION` 与 `BLOCK_PAGE` 的粒度、优化响应速度。

#### 4.4 那前缀匹配到底要不要改？

**设置拦截的前缀（机制 B）：保持现状，甚至要更宽，不要收紧。**
理由：前缀在这里是"值得检查的候选门"，作用是"把所有 OEM 的设置/管理器（`com.miui.securitycenter`、`com.huawei.systemmanager`、`com.hihonor.systemmanager`…）都识别成'要盯的设置'"。若改成精确匹配，新出一个 ROM 变体就漏一个，孩子正好从那个管理器里关权限——这正是产品要避免的。而且前缀过度包含在这里是**安全方向**：最多多盯几个设置子页，而那些子页由 4.3 的内容策略决定放不放行，不会放走任何东西。所以这块不收紧，反而要持续补 OEM 管理器包名。

**豁免白名单的两个输入法前缀（机制 A）：值得改，但理由是"完整性"，不是"防 spoofing"。**
- 不成立的那条理由："孩子造个 `com.android.inputmethod.evil` 冒牌包蹭前缀逃逸"——本产品面向普通儿童，造包名的能力不在这类用户的攻击面内，这条威胁不成立，不应作为修改依据。
- 成立的这条理由：硬编码只覆盖 AOSP/Gboard/搜狗/百度/讯飞等少数键盘，**漏掉了三星 `com.samsung.android.honeyboard`、OPPO `com.coloros.keyboard`、vivo `com.bbk.inputmethod`、魅族 `com.meizu.flyme.input`、荣耀 `com.hihonor.inputmethod` 等品牌自带键盘**。这些手机上键盘一弹就被当"陌生前台 App"拦掉 → **全机打不出字，连家长输密码都输不了**。这才是真实会发生、且普通儿童（只要用这类手机）就能触发的故障。
- 修法：运行时向系统要"已安装输入法清单"，拿到**精确**包名，不再靠猜：
  ```kotlin
  val imm = context.getSystemService(Context.INPUT_METHOD_SERVICE) as InputMethodManager
  val imePackages = imm.inputMethodList.map { it.packageName }   // 完整、精确、随装随更新
  ```
  落地：在 `WhitelistManager` 加一个输入法实时包名集合，服务启动时构建一次、监听 `ACTION_PACKAGE_ADDED/REMOVED` 刷新（带缓存，拦截热路径不查系统）；把 `isInWhitelist` 里两个输入法前缀判断改成查这个集合；原 `SYSTEM_WHITELIST` 里的精确名（搜狗/百度/讯飞等）保留作兜底。这样既补全了品牌键盘，又把豁免集统一成"全精确"，顺带消除唯一的前缀通配。优先级定为 P2（完整性修复）。

#### 4.5 顺带清理：死代码 + 误导性命名（P3）

- **死代码**：`isLauncher` / `isPhoneApp` / `isMessagingApp` / `isCommunicationApp` 这四个"家族前缀"方法，全工程**零调用方**（只有定义、没人调）。早期报告把它们当"绕过入口"，其实它们从未参与任何判定。建议直接删除。
- **命名误导（已修复）**：设置、安装器、市场分类已迁移至 `SystemSurfaceClassifier`，`WhitelistManager` 只保留“白名单=放行”职责；四个零调用方的家族方法也已删除。这样“表面分类=是否要盯”与“白名单=放行”已在代码层面分清。

#### 4.6 给后续维护者的速查结论

| 问题 | 结论 |
|------|------|
| "白名单前缀匹配绕过"是不是真漏洞？ | **不是**。前缀用在"拦截设置"而非"放行白名单"，方向相反；且面向普通儿童，包名伪装威胁不成立。 |
| 要不要把前缀改精确匹配？ | **不要**。改了会漏掉 OEM 管理器，孩子从那里关权限，是退化。设置前缀应保持甚至加宽。 |
| 真正该投入哪里？ | `ProtectedSettingsPolicy` 的关键词/ROM 覆盖 + `BLOCK_ACTION` 粒度调优（P1，攻防核心）。 |
| 输入法前缀要不要动？ | 要，但定性为"完整性修复"（补品牌键盘，别让手机打不出字），不是安全修复（P2）。 |
| `isLauncher` 等四个方法？ | 已删除（ISS-018）。设置/安装器/市场分类已迁移到 `SystemSurfaceClassifier`。 |

## 九、2026-07-11 复审勘误与修复结论

1. **ISS-001 已二次修复**：原“跨午夜但单调时钟增量不足 23 小时”会把正常换日误判为篡改。现改为比较墙钟增量与 `elapsedRealtime()` 增量，偏差超过 60 秒才冻结；新增正常跨午夜、前拨、倒拨、重启边界单测。设备重启后的前拨仍是纯本地方案的已知盲区。
2. **ISS-013 已二次修复**：原实现会直接删除仅存的旧明文密码，使儿童可能重设家长密码。现改为先写入 PBKDF2 hash、成功后再删除明文；迁移失败时保留旧值重试。
3. **ISS-011 已二次修复**：原懒加载把 Android 单例和 `Log` 带入白名单查询，造成 4 个 JVM 单测失败。现改为应用启动/包变更时刷新缓存，查询函数只读缓存；缓存未就绪时才保留旧前缀降级。
4. **ISS-014 为原报告误报**：`WRITE_SECURE_SETTINGS` 的程序化恢复实现早已存在，台账已标 `WONTFIX`，本次同步改正本报告。
5. **验证口径**：上述三项修复已通过 `testDebugUnitTest`；真机与 androidTest 仍需在有设备时按 ISS-006 / ISS-015 继续验证。
6. **ISS-018 已完成**：删除零调用的家族方法，并新增 `SystemSurfaceClassifier` 承担设置、安装器、应用市场的表面分类；所有调用方和单测已迁移，保持原有前缀匹配拦截语义。
