# KidsPhoneGuard 商业化计划任务书

创建日期：2026-04-23  
状态：草案，可持续追加  
目标：把当前 MVP 级儿童手机守护应用推进到可小范围付费试用、可渠道上架审核、可售后闭环的商业化版本。

---

## 1. 目标与原则

商业目标：

- 在中国大陆主流安卓应用市场尝试上架。
- 采用订阅制收费，并配套宽松退款政策。
- 通过真实用户反馈持续改进不同品牌手机的拦截稳定性。

产品原则：

- 不承诺绝对防破解，只承诺持续适配和问题可追踪。
- 不绕开系统安全模型，不做静默授权、Root、隐藏卸载等高风险能力。
- 数据默认本地化，诊断信息由家长主动导出或授权上传。
- 审核材料、用户文案、客服话术必须与实际能力一致。

## 6. 风险登记表

| 风险 | 等级 | 说明 | 缓解措施 |
|---|---|---|---|
| 应用市场拒审 | 高 | 无障碍、悬浮窗、阻止设置页可能被判高风险 | 准备审核说明、权限透明、紧急退出、避免恶意表述 |
| 拦截稳定性不足 | 高 | ROM 后台策略、小窗、权限掉权会影响效果 | 多机型测试、诊断包、兼容性公告、宽松退款 |
| 用户投诉“无效” | 高 | 家长购买后若设置不完整或机型不兼容，会认为被骗 | 购买前提示适配条件，提供配置体检和快速退款 |
| 儿童信息合规 | 高 | 产品目标涉及未成年人，隐私要求更严格 | 最小化收集，监护人同意，专门儿童规则 |
| 自动续费争议 | 中高 | 订阅制容易产生扣费争议 | 显著提示、取消说明、续费提醒、客服入口 |
| 多渠道支付复杂 | 中高 | 各应用市场 SDK、结算、退款不同 | 建立支付抽象层，先接入单渠道试点 |
| 官网/后端过重导致启动过慢 | 中 | 一开始做太重会分散主线精力 | 先做轻官网、最小后端、内部后台，不先做重用户中心 |
| 云端收集过多儿童数据 | 高 | 会显著增加合规、安全和舆情风险 | 采用最小化收集原则，默认本地存储，上传须家长授权 |
| 新手配置失败 | 高 | 普通家长不熟悉无障碍、悬浮窗、厂商保活设置，容易误以为产品无效 | 做首次设置向导、品牌权限页、配置后回检、拦截测试 |
| 售后成本过高 | 中 | 机型差异会带来大量人工支持 | 权限体检、机型库、诊断包、标准话术 |
| 被竞品或用户误解为恶意软件 | 中 | 阻拦设置页和悬浮窗容易引起误解 | 品牌定位透明，家长授权，文案克制 |

## 7. 近期执行建议

建议未来 2 周先做这些事：

1. 完成 release 工程、数据库 migration、日志脱敏和诊断包。
2. 把权限体检页做成商业版核心页面，而不是隐藏的排障功能。
3. 建立至少 4 台不同品牌手机的稳定性测试表。
4. 设计首次设置向导和品牌权限配置页，先覆盖小米、华为、OPPO、vivo。
5. 起草隐私政策、儿童个人信息保护规则、用户协议和退款政策，并搭建可访问的政策站。
6. 定义最小后端数据模型，只做订单、订阅、退款、设备绑定、工单，不先上复杂账号体系。
7. 选择首个试点市场，优先研究该市场对无障碍、悬浮窗、后台保活、订阅支付的审核要求。

建议 1 个月内达到：

- 可以给 20 个真实家庭试用。
- 可以明确告诉用户哪些机型已验证，哪些机型有风险。
- 可以处理购买、退款、诊断、回访。
- 官网、后端、内部后台形成最小闭环。
- 新手用户可以按向导独立完成首次配置和一次拦截测试。
- 可以向第一个应用市场提交审核材料。
