## 1. 任务背景

- 产品：KidsPhoneGuard（拉钩守护），本地 Android 家长管控 App，核心防卸载诉求：孩子不能通过
  **设置→应用管理** 或 **桌面长按→卸载** 两条通道卸载本应用。
- ISS-020 结论：用户明确否决 Device Owner / 恢复出厂方案（不可接受数据清空），要求**纯软件方案**，
  并且**抛弃全部旧防卸载代码从零重建**（旧代码历史上越改越偏，修补式演进已不可救药）。
- 验收环境双机：荣耀（PKT0220109015551，launcher = com.huawei.android.launcher）和
  小米 Redmi Note 12 Turbo（23049RAD8C，MIUI，launcher = com.miui.home）。

## 2. 最终结果（诚实状态）

| 项目 | 荣耀 | 小米 |
|---|---|---|
| 设置→应用管理 卸载拦截 | ✅ 用户验收通过 | 未复测通过 |
| 桌面长按→卸载 拦截 | ✅ 确认框不弹出即被拦 | ❌ **确认框弹出且不拦截，可随意卸载（比初版更糟）** |
| 普通应用拦截遮罩节奏 | ✅ 正常 | ❌ 首次遮罩超长 + 二次遮罩（日志实证仍未解决） |

**结论：小米侧失败。三轮修改后卸载拦截能力出现净退步。用户已中止本路线。**

## 3. 三轮演进与每轮的根因假设

### 第 0 版（ae5b31a，荣耀通过）
- 架构：`UninstallDecisionEngine`（纯 Kotlin 决策引擎，JVM 可测）+ `UninstallGuard`（薄壳接线）。
- 判定：安装器家族窗口 / launcher 窗口中出现"卸载/删除"关键词 + 本应用标识 → 弹全屏遮罩 + BACK/HOME。
- 荣耀双通道拦截通过用户验收。

### 小米暴露的问题与三轮"修复"

**问题 A：遮罩长时间不退。** 根因①：遮罩释放条件是"目标应用离开前台"，但 launcher 被拦后
HOME 归宿仍是 launcher，条件永不成立。修复①：改为决策驱动释放（900/1600/2600/4200ms 复查，
威胁消失即释放）。——此修复方向正确，保留。

**问题 B：安装本应用被误杀。** 根因②：安装器页面规则未区分"安装/更新"与"卸载"语义，
`pm install` 触发的安装器页被当成卸载页拦截挂起。修复②：安装器路径要求出现卸载关键词才拦。
——此修复方向正确，保留。

**问题 C（性能）：遮罩显示 5 秒、隐藏 8.7 秒、二次遮蔽、返回键迟钝、MIUIScout ANR。**
日志实证：单次全窗扫描 **1.4~3.3 秒**（MIUI 上 `AccessibilityNodeInfo` 逐节点 IPC 约 7ms，
整屏约 400 节点），周期 sweep 每 480ms 对所有窗口抓整树，主线程被 IPC 打爆。
修复③（**出问题的就是这一轮**）：
1. sweep 只看安装器家族窗口，节奏放宽到 1500ms；
2. **绝不遍历 launcher 主窗口**，只遍历"非全屏对话框小窗"，单次预算 250 节点；
3. 新增**长按归因**：LONG_CLICK 事件文本含"拉钩守护"则记录 8 秒归因窗口，
   之后点击"卸载"凭归因直接判定，不再扫树。

### 第 3 轮为什么反而更糟（核心教训）

修复③的两个关键假设**都没有真机验证就写进了判定链路**：

1. **假设"长按事件的文本里带应用名"**。MIUI 的 LONG_CLICK 事件/源节点文本未必包含"拉钩守护"
   （很可能是图标 View，text 为空，contentDescription 才有标签，甚至什么都没有）。
   归因窗口从未被记录 → 后续点击"卸载"时归因恒为 false。
2. **假设"不扫 launcher 主窗口也能拿到应用身份"**。原版判定中，卸载确认对话框里的
   应用身份（"拉钩守护"字样）是靠遍历对话框/launcher 窗口树拿到的。第 3 轮把
   launcher 主窗口遍历整体砍掉后，点击事件路径上**唯一的身份来源消失**，
   规则 4（点击卸载词 + 身份/归因 → 拦）恒不成立 → **确认框完全不拦**。
   这就是"越解决越糟"的直接机制：为了解决"扫得太慢"，把"判定的眼睛"一起摘了。

日志佐证（2026-07-23 02:0x，存档文件内）：
- 卸载测试期间 **没有任何一条 `uninstall_decision` 日志** —— 不是判错，是根本没判。
- `ShortcutService: Detected launcher: com.miui.home ... from callingPackage: com.kidsphoneguard`
  每约 3 秒一条，伴随密集 GC —— 应用内某个轮询（疑似 UsageTrackingManager 3 秒轮询链路）
  在 MIUI 上持续触发 launcher 快捷方式查询与 GC 抖动，是"主屏静置也卡"的独立嫌疑，
  与遮罩问题无关但会加重整体卡顿观感。**接手者应单独排查这一调用源。**
- Focus Todo 拦截日志显示二次遮罩仍存在：02:02:36 count=2，显示耗时 1.4s，
  持续约 10 秒才隐藏 —— 决策驱动释放在"拦截后仍停留在被拦应用"场景下会再次判定为威胁
  并重显示遮罩，释放条件与再触发条件之间存在环。

## 4. 给接手者的负面清单（不要重复这些做法）

1. **不要在未 dump 真实 UI 结构前设计判定规则。**
   正确第一步：`adb shell uiautomator dump` 在小米上分别抓取
   ① 长按菜单弹出时 ② 卸载确认框弹出时 的完整 UI 层级，
   确认：确认框属于哪个包（com.miui.home？com.miui.packageinstaller？）、窗口类型、
   "卸载"按钮与"拉钩守护"字样各在哪个节点、节点 text/contentDescription 实际内容。
   荣耀与 MIUI 的确认框宿主很可能不同，一套规则通吃是幻想。
2. **不要依赖无障碍事件的 text 字段承载关键信息。**
   事件 text 在各 ROM 上极度不稳定。凡涉及"身份归因"，以窗口树 dump 到的真实节点为准。
3. **不要用"减少扫描范围"来治"扫描太慢"，除非先证明被砍掉的路径不是判定必需。**
   性能优化的正确顺序：先保证判定正确 → 再用缓存/去抖/异步化降成本 → 最后才砍扫描范围，
   且每砍一处都要回归双通道卸载用例。
4. **不要把 JVM 单测通过当成真机正确。** 20 个单测全绿，真机全败。
   单测只能验证引擎逻辑自洽，验证不了"事件里有没有那段文本"这类环境假设。
5. **不要忽视旁路信号。** ShortcutService 每 3 秒被调用 + 密集 GC 这类日志是免费的健康检查，
   早就提示了轮询链路在 MIUI 上有额外成本。
6. **荣耀通过 ≠ 小米通过。** 两台机器的拦截时序完全不同（荣耀点卸载图标即拦、确认框不弹出；
   MIUI 确认框先弹出）。任何改动必须双机回归，且以用户人工验收为准（AGENTS.md Rule 5）。
7. **遮罩"显示条件"与"释放条件"要成对审查。** 只改释放条件会留下"释放→再触发→再显示"的环
   （二次遮罩即由此来）。

## 5. 仍然成立、可保留的资产

- `UninstallDecisionEngine` 纯函数引擎 + JVM 单测的**架构形态**是对的，失败的是喂给它的
  事实假设，不是分层本身。
- 决策驱动遮罩释放（替代"目标离开前台"轮询）方向正确。
- 安装/更新页与卸载页的语义区分（防 pm install 误杀）正确且必要。
- `uninstall_sweep_slow_scan` 慢扫描日志是好工具，保留。
- 全局解锁作为家长逃生口的放行规则正确（本次小米"完全不拦"期间全局解锁是关闭的，
  排除误放行因素）。

## 6. 建议的重新出发顺序

1. 回滚工作区到 `ae5b31a`（荣耀基线）。
2. 在小米上 `uiautomator dump` 抓取卸载全流程 UI 层级（§4.1），写成事实文档。
3. 基于 dump 事实重写 MIUI 判定规则；扫描成本用"按需懒扫描 + 结果短缓存"控制，
   不砍必要路径。
4. 排查并消除每 3 秒一次的 launcher 快捷方式查询源。
5. 每步改动后双机回归三个固定用例：设置通道卸载、长按通道卸载、普通应用拦截遮罩节奏。
6. 一切状态结论以用户人工验收为准，任何自动化证据不用于关单（AGENTS.md Rule 5 / ISSUES.md §0.9）。
